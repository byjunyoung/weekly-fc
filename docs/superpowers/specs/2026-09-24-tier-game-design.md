# 티어 게임 — 1:1 대결로 능력치를 정한다

> 2026-09-24. 사용자: "능력치가 사람마다 느끼는 게 다를 거거든? 티어를 나누는 게임을 하나 만들어서
> 공유하고 그 결과 기반으로 능력치 반영되게." 방향 질문 다섯의 답 — **대결로 하고 결과는 티어표로 공유**,
> **대결마다 바로 반영 · 스텝퍼는 없애고 게임으로 가는 길을 연결**, 장난 막기는 **이름만**,
> 공유는 **이미지 + 링크**, **나도 내 대결에 나온다**, 이미지엔 **전체 티어표**.

## 1. 왜 · 무엇이 바뀌나

지금은 누구나 선수 페이지 스텝퍼로 숫자를 직접 고친다. 사람마다 기준이 달라 숫자가 누가 마지막에
고쳤느냐로 정해진다. 실제로 값이 70 에 몰려 있다(2026-09-24: 여섯 항목 중간값이 전부 70, 종합 70 이 일곱 명)
— 기본값이 그대로 남은 흔적(추정).

게임은 절대 점수를 묻지 않고 "둘 중 누가 더 나은가"만 묻는다. 모의실험(선수 30·평가자 20, 사람마다
후하게/짜게 주는 버릇과 잡음을 넣음)에서 순서 정확도는 점수 평균(0.98)이 대결(항목당 1인 25~40판에
0.93~0.96)보다 약간 높았다 — 평균이 개인 버릇을 상쇄하기 때문. **대결을 고른 이유는 정확도가 아니라
가볍고 게임 같아 많이 하게 된다는 점**이다. 참여가 적으면 어느 방식이든 흔들린다.

## 2. 화면

```
상단 탭: 홈 · 명단 · 라인업 · 팀짜기 · 티어 · 운영 규칙

/tier/
├ 결과 티어표 [종합 | 페이스 | 드리블 | 패스 | 슈팅 | 수비 | 체력]
│   S/A/B/C/D 줄마다 아바타+이름. 숫자는 안 보인다(칸이 곧 숫자 구간)
│   [이미지로 공유] → 1080×1350 PNG + "나도 하기" 링크 글
└ [대결 시작]
    "나"가 없으면 먼저 고른다(상단바 '나'와 같은 값)
    "누가 더 빠르다?"  [A]  vs  [B]   [모르겠음]
    누르면 두 사람의 변화(+2 / −2)를 잠깐 보여 주고 다음 판

선수 페이지: 스텝퍼 제거 → [티어 게임에서 바꾸기] → /tier/?num=N
  N 이 낀 대결을 항목마다 한 판씩(여섯 판) 먼저 낸 뒤 보통 순서로.
  기록 줄: "페이스 70 → 72 · 민수 · 대결"
```

**폰 폭 탭** — 여섯 탭이 한 줄에 들어가려면 약 414px 가 필요하다(실측). 459px 이하에선 탭 줄을 가로로
밀게 두고, 오른쪽에 더 있으면 끝을 흐리게, 지금 탭은 보이는 자리로 밀어 둔다(두 줄 접기 대신 — 설계 승인 때 고른 것).
티어표의 항목 일곱 칸도 같은 이유로 제 줄에서 가로로 민다.

## 3. 계산 — 능력치 숫자가 곧 레이팅

- 기대 승률 `E = 1 / (1 + 10^((b − a) / 40))` — 20점 차면 강한 쪽 76%.
- 이긴 쪽 `+Δ`, 진 쪽 `−Δ`, `Δ = max(1, round(4 × (1 − E)))`. 비슷한 사이 2, 예상대로 1, 이변 3~4.
- 1~99 를 벗어나지 않는다(넘치는 쪽만 잘린다).
- 지금 숫자에서 출발 — 다시 매길 필요 없음. 오른 만큼 내리니 팀 평균이 부풀지 않는다.
- 같은 식을 SQL(`private.vote_delta`)과 앱(`src/lib/tier.ts voteDelta`)에 둔다. 앱 쪽은 화면에
  미리 보여 주는 용도가 아니라 테스트 대조용 — **값은 서버 응답을 쓴다.** 두 식의 상수(40·4)가 같은지
  테스트가 SQL 파일을 읽어 대조한다.

**짝 고르기(브라우저)** — 항목은 여섯을 돌아가며. A 는 이번 세션에서 덜 나온 선수 중 무작위, B 는 그 항목
숫자가 A 와 가까운 여섯 중 무작위(가까운 사이일수록 비교가 의미 있다). 직전 여섯 판에 나온 같은 쌍은 피한다.
나도 나온다(결정 5).

## 4. 서버

마이그레이션 `supabase/migrations/20260924100000_tier_game.sql`.

- `stat_log.via text not null default ''` — `'game'` 이면 대결로 바뀐 줄. `get_all` 이 함께 보낸다.
- `public.vote(p_field text, p_win int, p_lose int, p_by int default null)` → `{ts, win:{num,before,after}, lose:{…}}`
  - 항목이 여섯 중 하나가 아니면 `'모르는 능력치입니다'`, 같은 번호면 `'같은 선수끼리는 대결할 수 없습니다'`,
    없는 번호면 `'그 번호의 선수가 없습니다'`.
  - 두 선수 행을 **번호 순으로** 잠근다(동시 대결이 서로 기다리다 멈추지 않게).
  - 바뀐 칸마다 기록 한 줄(`via = 'game'`, `by`·`by_name` 은 고른 "나").
- `get_all` 의 기록은 "전체 최근 300줄" → **선수마다 최근 8줄**. 대결은 한 판에 두 줄을 남겨 전체 300줄이면
  150판 만에 대부분 선수의 기록이 창밖으로 밀린다. 화면이 쓰는 건 선수 페이지의 그 선수 8줄뿐이다.
- `write_stats` 의 `anon` 실행 권한을 걷는다(스텝퍼가 없어진다). 관리자 편집 창은 `write_player` 로 숫자를 고친다 — 그대로.

**티어 기준**(종합 = 여섯 평균, 항목 탭도 같은 선): S ≥ 85 · A 78~84 · B 70~77 · C 63~69 · D ≤ 62.
2026-09-24 값으로 S 5 · A 7 · B 11 · C 7 · D 0(종합이 62.5 인 다섯 명이 반올림으로 63 → C). 대결이 쌓이면 벌어진다.

**공유 이미지** — 1080×1350, 제목 "WEEKLY FC 티어 · 날짜", S~D 줄에 아바타+이름, 숫자 없음. 공유 글에
`/tier/` 주소. 라인업 이미지가 숫자를 빼던 이유(단톡방에 숫자가 도는 게 민감할 수 있음)는 여전히 지킨다 —
티어 칸 자체를 올리는 건 사용자가 고른 것.

## 6. 확인

- 단위: `voteDelta`(이기면 오른다·0 이 아니다·1~99·합이 0), SQL 상수 대조, `tierOf` 경계, `pickPair`
