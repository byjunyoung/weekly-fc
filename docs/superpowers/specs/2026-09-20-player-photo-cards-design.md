# WEEKLY FC — 실사 선수 카드 (D단계)

> **[2026-09-21 대체됨]** 전체 비주얼 리프레시(도트 게임 컨셉, `2026-09-21-pixel-refresh-design.md`)에서
> 사용자가 실사 사진 기능 자체를 삭제하기로 결정했다 — 이 스펙이 정한 기능은 배포 하루 만에
> 되돌려진다. 이 문서는 그 결정이 있었다는 기록으로만 남긴다.

## 1. 무엇을 뒤집나

9/11 스펙(`2026-09-11-game-ui-redesign.md`)은 "공개 레포엔 실명·사진을 못 쓴다"는 전제로
부품 조합 SVG 아바타를 골랐다(같은 문서 25·50·131행). 이번 단계는 그 전제를 뒤집는다 —
매치 영상에서 뽑은 실사 사진을 선수 카드에 쓴다. 팀 차원에서 이미 유튜브에 영상을 공개로
올리고 있어 노출 수준이 같다고 보고, 선수별 개별 동의 절차는 두지 않는다(사용자 결정).

바뀌지 않는 것: `avatar` 시트 열, SVG 부품 에디터, 서버 계약(`isValidAvatarCode` 등) —
전부 그대로 둔다. 사진은 그 위에 얹히는 프론트엔드 전용 장식이라 백엔드 변경이 없다.

## 2. 확정된 결정 (사용자 답변)

| 질문 | 답 |
|---|---|
| 동의 절차 | 선수별 개별 동의 없이 팀 차원 일괄 처리 |
| 저장 위치 | git 레포에 직접(파일 히스토리가 그대로 남음) |
| 업로드 방식 | 앱 안 업로드 UI 없음 — 관리자가 파일을 수동으로 레포에 배치 |

세 번째 결정에서 자연히 따라오는 것: 사진이 있는 선수와 없는 선수가 섞여 있는 게 기본
상태다. 한 번에 전원이 채워지는 기능이 아니라, 관리자가 사진을 하나씩 구하는 대로 늘어가는
점진적 기능이다.

## 3. 저장 규약

- 경로: `public/players/{선수번호}.jpg` — 확장자는 `.jpg` 하나로 고정한다. 여러 포맷을
  받으면 폴백 로직(4절)이 확장자마다 분기해야 해 복잡해진다. 관리자는 저장할 때 JPG로
  내보내면 된다.
- 선수 번호는 탈퇴 시 재사용된다(`nextFreeNum`이 빈 번호를 찾아 새 선수에게 준다). **선수를
  삭제할 때는 `public/players/{번호}.jpg`도 함께 지우는 걸 운영 수칙으로 못 박는다** — 안
  그러면 새로 들어온 선수한테 옛 선수의 얼굴 사진이 그대로 넘어가는 사고가 난다. SVG 코드
  재사용은 추상적이라 문제가 안 됐지만, 사진은 다르다.
- 크기 권장: 매치 영상 스크린샷 원본(최대 1080p)을 그대로 커밋하면 표시 크기(최대
  112~120px)의 10배가 넘게 무거워진다. 커밋 전에 가로 400~600px 정도로 줄이는 걸 권장
  사항으로 스펙에 적어두되, 앱이 강제하진 않는다(수동 배치 프로세스의 일부).

## 4. 렌더링 방식 — 사진을 SVG 위에 얹고, 없으면 사라지게

지금 아바타는 `avatarSvg()`가 만드는 SVG 문자열을 `playerCard()`의 `avatarHtml` 인자로
넘기거나(`.pcard-portrait` 안) 목록 칸에 직접 꽂는 식으로, 전부 문자열 조립이다
(`dangerouslySetInnerHTML`). 사진도 같은 방식의 문자열로 만들어 SVG **앞에 겹쳐** 넣는다:

```html
<img class="pcard-photo" src="/weekly-fc/players/9.jpg" alt="" onerror="this.remove()" />
<svg ...>...</svg>  <!-- 기존 avatarSvg() 출력, 그대로 유지 -->
```

- 사진 파일이 있으면 `<img>`가 로드되어 SVG를 가린다.
- 파일이 없으면(404) `onerror`가 즉시 `<img>`를 DOM에서 제거해 밑에 이미 그려져 있던 SVG가
  그대로 드러난다.
- 별도 매니페스트·데이터 필드·존재 여부 체크 코드가 필요 없다 — **파일이 있다는 사실 자체가
  "사진 있음"이다.** 관리자는 파일을 넣고 빼는 것만 하면 되고, 그 결과가 배포 즉시 반영된다.
  (대안으로 어떤 선수가 사진을 가졌는지 매니페스트 JSON으로 추적하는 안도 검토했지만, 파일
  작업 때마다 매니페스트를 같이 고쳐야 해 어긋날 여지가 생긴다 — 기각.)
- 틀: 사진은 정사각 틀에 `object-fit: cover`로 채운다. 관리자가 사진을 미리 정확히 자를
  필요 없이, 앱이 중앙 기준으로 잘라 보여준다.
- React 컴포넌트(`PlayerDetail.tsx`)에서 조립하는 문자열도, 원시 HTML 조립 함수
  (`player-card.ts`)에서 조립하는 문자열도 이 패턴이 그대로 통한다 — `onerror` 속성은 순수
  HTML이라 프레임워크에 안 걸린다.
- 경로는 기존 `src/lib/url.ts`의 `href()` 헬퍼(base 경로 `/weekly-fc` 자동 부착)를 그대로
  쓴다 — 새 경로 조립 로직을 만들지 않는다.

## 5. 적용 위치

현재 아바타가 나오는 4개 자리는 다음과 같다 — 이 중 한 곳(편집 모달)만 아래에서 예외로
뺀다:

| 파일 | 자리 | 현재 SVG 크기 |
|---|---|---|
| `src/react/player/PlayerDetail.tsx:208` | 아바타 편집 모달 미리보기 | 120px |
| `src/react/player/PlayerDetail.tsx:237` | 선수 상세 카드 초상(편집 버튼 안) | 112px |
| `src/react/squad/RosterList.tsx:39` | 스쿼드 명단 표의 28px 칩 | 28px |
| `src/react/squad/RosterList.tsx:74` | 스쿼드 카드형 초상 | 116px |

단, **아바타 편집 모달 미리보기(120px)만은 사진을 얹지 않고 SVG만 보여준다** — 그 모달은
"SVG 부품 코드"를 편집하는 화면이라 사진이 끼면 뭘 고치는 중인지 헷갈린다. 나머지 네 자리는
전부 사진-우선-SVG-폴백으로 통일한다.

`.pcard-portrait`(카드 초상 컨테이너)에 `position: relative`를, 새 `.pcard-photo` 클래스에
`position: absolute; inset: 0; object-fit: cover`를 준다 — 모바일 카드벽에서 SVG를 68px로
줄이는 기존 규칙(`tokens.css:339`)과 짝을 맞춰 사진도 같이 줄어들게 한다. 28px 표 칸은
`<span>` 래퍼에 `position: relative; display: inline-block`을 추가한다. 정확한 CSS는
구현 계획에서 확정한다.

## 6. 사진 선별 가이드 (관리자용, 앱이 강제하지 않음)

관리자가 사진을 고를 때 참고할 기준을 스펙에 적어 둔다(영상·미디어에 얼굴을 최대한 안
비추는 기존 팀 방침과 같은 선):

- 뒷모습·측면·원거리 샷을 우선한다. 정면 클로즈업은 피한다.
- 사진 한 장에 여러 명이 잡혀도 상관없다 — 어차피 크롭은 앱이 중앙 기준으로 하므로, 원본은
  본인이 중앙 근처에 있는 프레임을 고르면 된다.
- 이미 편치 않다고 느껴지는 선수는 사진을 아예 안 넣으면 그만이다(파일이 없으면 자동으로
  기존 SVG 아바타로 남는다) — "전원이 사진을 가져야 한다"는 목표가 아니다.

## 7. 범위 밖

- 앱 안 업로드·크롭 UI (수동 배치로 확정)
- 얼굴 자동 블러·모자이크 처리 (관리자가 사진 선택 단계에서 거르는 것으로 대체)
- 선수별 개별 동의 기록·추적 (팀 차원 일괄 처리로 확정)
- 어떤 선수가 사진을 가졌는지 추적하는 매니페스트/데이터 필드 (파일 존재 자체가 신호)
- 사진 유무를 선수 목록/필터 기준으로 노출하는 것 (요청에 없음)

## 8. 검증

- 실제 사진 파일 하나를 `public/players/`에 넣고, 위 4개 자리(모달 미리보기 제외)에서 사진이
  뜨는지 확인한다.
- 파일이 없는 선수는 기존 SVG 아바타가 그대로 뜨는지 확인한다(회귀 없음).
- `onerror` 폴백 자체를 CDP로 확인한다 — 존재하지 않는 경로의 `<img>`가 실제로 제거되고
  밑의 SVG가 드러나는지.
- 페이지 무게: 사진 파일을 추가해도 3~4단계에서 다져온 페이지 용량 관리 관행(빌드마다
  `page-js.mjs`로 측정)에 사진 바이트가 새로 잡히므로, 큰 파일이 들어오면 빌드 후 크기를
  같이 보고한다.
