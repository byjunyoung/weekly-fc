# WEEKLY FC — 게임 인터페이스 재설계

2026-09-11. 1차 포탈(2026-09-10 스펙)이 배포됐으나 "게임이 아니라 관리자 대시보드 같다"는 판정. 밀도·대비·재미가 없다는 것이 요지. FM·EA SPORTS FC·eFootball 인터페이스를 조사해(`docs/research/2026-09-11-football-game-ui-reference.md`, 출처 19개) 그 문법으로 다시 짠다.

이 문서는 2026-09-10 스펙을 **대체하지 않고 덧씌운다**. 정보구조(6갈래)·데이터 계약·배포 절차는 그대로다. 바뀌는 것은 표현과, 새로 붙는 두 기능(아바타·컨디션)이다.

## 1. 무엇이 잘못됐나

1차 결과의 홈은 흰 화면에 1px 상자 셋이고 나머지가 빈 공간이다. 스쿼드 표는 밀도는 있으나 거의 무채색이고 숫자가 작다. 선수 페이지는 모든 요소가 같은 크기다. 즉 **위계가 없고 색이 일을 안 한다.**

리서치가 준 진단:
- FM은 화면 대부분이 무채색이되 **색이 들어가는 자리는 전부 "즉시 판단해야 하는 지점"**이다(능력치 등급·컨디션·경고). 색 면적이 작은 것과 색이 없는 것은 다르다.
- FC는 **큰 숫자 하나가 화면 위계를 지배**하고 등급이 곧 색 정체성이다(골드 75+ / 실버 65~74 / 브론즈 64-).
- eFootball은 정적 데이터 위에 **동적 레이어**를 얹어 긴장감을 만든다(경기 전 컨디션 화살표).

우리는 셋 다 안 하고 있었다. 그리고 `grade()`가 이미 골드/실버/브론즈를 계산하는데 화면 어디에도 안 쓰인다.

## 2. 방향

| 층 | 벤치마크 | 우리 적용 |
|---|---|---|
| 화면 골격·표 | FM | 짙은 바탕, 밀도 높은 표, 색은 신호로만 |
| 선수 카드 | FC | 큰 OVR + 등급 프레임 + 아바타 초상 |
| 컨디션 | eFootball | 최근 출석에서 파생되는 동적 화살표 |
| 초상 | — | 부품 조합 SVG 아바타(실사진 불가 제약을 이점으로) |

## 3. 팔레트 — 짙은 바탕

사용자 결정(2026-09-11). 1차의 밝은 바탕이 "대시보드처럼 보인다"의 주원인이었다.

색은 `src/styles/tokens.css` 한 곳에서만. 구조는 그대로 두고 값만 뒤집으므로 파일 하나가 중심이 된다.

```
--bg        가장 어두운 면 (앱 바탕)
--surface   한 단 밝은 면 (카드·표 헤더·사이드바)
--tint      두 단 밝은 면 (호버·선택)
--fg        주 텍스트 (거의 흰색)
--muted     보조 텍스트
--line      경계선 — 짙은 바탕에서는 밝은 쪽으로 1px
```

**원칙: 채도 높은 색의 화면 면적은 작게 유지한다(FM).** 색이 들어가는 자리는 정해져 있다 — 능력치 등급, 컨디션, 미납 경고, 포지션 배지, 카드 등급 프레임. 그 외에는 무채색.

기존 의미색(`--pos-*` 포지션 4색, `--val-a~d` 4구간, `--warn`)은 **의미를 유지하되 짙은 바탕에서 읽히도록 값을 다시 잡는다.** 밝은 바탕용 값을 그대로 쓰면 탁해진다.

라이트 모드는 만들지 않는다(1차 결정 유지).

## 4. 아바타

실사진은 애초에 못 쓴다(공개 레포에 실명·사진 불가). 부품 조합 SVG가 그 자리를 채운다. "허접해도 좋다"는 것이 사용자 지시이므로 **정교함보다 조합의 가짓수와 알아보는 재미**를 택한다.

### 저장 형식
`선수명단` 시트에 `avatar` 열 하나. 짧은 코드 문자열:
```
f2:h5:s3:e1:k#1a1a1a
얼굴형:헤어:피부:눈:유니폼색
```
파싱 실패·빈 값이면 기본 아바타(번호만 든 원)로 떨어진다. 한 칸이므로 스키마 변경이 최소다.

### 편집 권한 — 잠금 없음 (사용자 결정)
누구나 명단에서 사람을 골라 아바타를 바꿀 수 있다. 가입·코드 없음.

**단, 전용 액션으로 아바타 칸만 쓴다.** `writeAvatar(num, code)` 는 PIN 없이 동작하되:
- `선수명단`의 해당 행 `avatar` 열 **하나만** 갱신한다. 다른 열은 읽지도 쓰지도 않는다.
- `code` 를 형식 검증한다(허용 부품 id·색 hex 형태만). 통과 못 하면 거부.
- 길이 상한을 둔다.

기존 `writePlayer`(PIN 필요)는 그대로다. 잠금 없는 엔드포인트가 능력치·이름·전화를 건드릴 수 있으면 안 된다.

### 등장 위치
스쿼드 표 행 · 선수 페이지 카드 · 라인업/전술판 선수 원 · 리캡 카드 · 홈의 "내 자리".

## 5. 선수 카드 (FC 문법)

선수 페이지 상단과 스쿼드 카드 보기에서 쓴다.

```
┌──────────────────┐
│ 89          ← 큰 OVR 이 위계를 지배
│ MF          ← 포지션
│                  
│    [아바타]       
│                  
│  김효종           
│  PAC DRI PAS     ← 능력치 6종, 2열
│  SHO DEF PHY     
└──────────────────┘
등급 프레임: 골드 84+ / 실버 69~83 / 브론즈 68-
```

등급 경계는 **기존 `grade()` 값을 그대로 쓴다**(84/69). FC의 75/65 를 가져오지 않는다 — 우리 능력치 분포가 다르고, 이미 코드에 있는 경계를 바꾸면 모든 선수의 등급이 흔들린다.

등급은 프레임 색으로만 표현한다. 카드 배경 전체를 금색으로 덮는 FC 방식은 짙은 바탕의 절제와 충돌하므로 택하지 않는다(테두리와 OVR 숫자 색까지).

## 6. 컨디션 (eFootball 문법)

정적 능력치 위에 얹는 동적 레이어. **최근 매치 출석에서 파생**한다.

```
최근 4경기 중 출석  화살표   의미
  3~4              ▲ 청록   꾸준히 나옴
  2                ▬ 노랑   보통
  0~1              ▼ 빨강   최근 안 보임
기록 없음           —       판단 보류
```

능력치를 실제로 바꾸지 않는다. 표시만 한다 — 벌점처럼 읽히면 안 되고, "요즘 자주 보이는 사람"을 알아보는 장치다.

스쿼드 표·선수 카드·매치 참석자 목록에 나온다.

## 7. 밀도와 위계

- **홈**: 빈 공간을 정보로 채운다. 최근 매치 결과·이번 달 봉사·미납·내 자리에 더해, 출석 상위 몇 명·최근 영상·다음 봉사 차례를 한 화면에. FM 홈이 그렇듯 스크롤 없이 "지금 상태"가 보여야 한다.
- **스쿼드 표**: 아바타 · 번호 · 이름 · 포지션 · 컨디션 · 능력치 6 · OVR · 출석률. 행 높이를 낮추고 숫자를 tabular figures 로. OVR 은 등급 색.
- **선수 페이지**: 카드가 주인공. 능력치는 막대와 수치를 함께(FM 격자의 변형). 참여 이력·벌금은 그 아래 보조.

## 8. 인터랙션

사용자 요청("게임처럼 인터랙션도 풍부하면"). 과하면 느려지므로 **상태 변화가 있는 자리에만** 둔다.

- 숫자 카운트업: OVR·출석률·정산 합계가 0에서 실제 값으로
- 능력치 막대 차오름: 선수 카드 진입 시
- 카드 뒤집기: 선수 카드 앞면(능력치) ↔ 뒷면(참여 이력 요약)
- 표 정렬 시 행 이동 트랜지션
- 아바타 편집기에서 부품을 바꿀 때 즉시 반영

접근성: `prefers-reduced-motion` 을 존중해 전부 끈다. 1차 스펙의 "모션 없음" 규칙은 이 절로 대체된다.

## 9. 범위 밖

로그인·계정 · 실사진 업로드 · 능력치 자동 산출 · 라이트 모드 · 1차 스펙이 이미 제외한 것들(예정 경기·포탈 내 투표·알림·댓글·득점/MOM·카톡 자동 연동).

## 10. 검증

- 짙은 바탕에서 의미색 4구간·포지션 4색·경고색이 모두 판별되는지 화면으로 확인
- 아바타: 부품 조합 30명분을 한 화면에 렌더해 서로 구별되는지
- `writeAvatar` 가 다른 열을 건드리지 않는지 실제 시트로 확인
- `prefers-reduced-motion` 에서 모션이 꺼지는지
- 1차의 검증 항목(가로 넘침 0·noindex 경계·전화 미노출)은 계속 통과해야 한다
