# WEEKLY FC — 스쿼드 한 화면 · 운영 탭 · 기록 걷어내기

2026-09-13. 게임 UI 재설계(2026-09-11) 배포 뒤 사용자 판정:

- 기록은 어차피 안 쌓인다 → 지운다. 실제로 시트에 매치·봉사·벌금·라인업이 0건이고 선수 30명만 있다(2026-09-13 `getAll` 응답).
- 소개는 운영 규칙 중심이 낫다.
- 봉사자는 두 명인데 홈에서 한 명만 주연으로 보인다.
- 스쿼드와 전술을 한 탭에서 바로 하고 싶다. 매치마다 스쿼드를 짜서 이미지로 공유하고 싶다.
- 전술판 UI가 다 깨진다.

이 문서는 앞선 두 스펙을 **덧씌운다**. 데이터 계약(시트 열)과 백엔드는 그대로 두고, 정보구조와 스쿼드·전술 화면을 바꾼다. 실사 선수 카드(D단계)는 이 문서 범위 밖이다(§8).

## 1. 결정 기록

| 항목 | 결정 | 근거 |
|---|---|---|
| 순서 | 구조·전술판·봉사 먼저, 실사 카드는 뒤 | 기존 코드 안에서 끝나고 매주 바로 쓴다. 실사는 화질 확인이 먼저 |
| 기록 범위 | **출석 기반 전부 걷기**. 벌금·봉사 관리는 운영 탭으로 | 빈 지표가 남지 않게 |
| 합치는 방식 | **한 화면에 명단 + 피치** | "한 탭에서 바로" |
| 스쿼드 단위 | **한 팀 라인업만**. 상대 팀·팀 나누기 없음 | 사용자 결정 |
| 저장 | **이미지 공유만**. 서버 저장 없음, 기기에 초안 하나 | 매치·라인업 기록을 안 쓰기로 해서 다시 볼 곳이 없다 |
| 운영 탭 | **규칙 섹션 안에 현황을 붙인다**(한 페이지) | 규칙과 실제 현황이 한곳에 |

모두 사용자 결정(2026-09-13).

## 4. 스쿼드 한 화면

### 4.1 레이아웃

```
데스크톱 ≥ 900px
┌ 스쿼드 ──────────────────────────────────────────────────────┐
│ 인원 [− 6 +]  포메이션 [2-2-1 ▾]  경기장 [풋살|축구]  [자동 배치]  │
├──────────────────┬───────────────────────────────────────────┤
│ 명단 [전체 GK DF…]│              피치                          │
│ 보기 [목록|카드|표]│                                           │
│ 선수 행/카드       │  도구 [이동|화살표|펜] [되돌리기] [지우기]    │
│                  │                               [이미지 공유]  │
└──────────────────┴───────────────────────────────────────────┘

모바일 < 900px
상단 컨트롤(두 줄까지 줄바꿈) → 피치(폭 맞춤) → 도구 한 줄 → 명단(아래에서 끌어올리는 시트)
```

명단 보기 「카드」「표」는 지금 스쿼드 페이지의 카드 벽·표를 옮긴 것이다. 행을 누르면 배치(§4.3), 이름 링크는 선수 상세로 간다.

### 4.2 인원 · 포메이션 · 경기장

- 인원 5~11. 포메이션 목록은 인원에 따라 바뀐다. 모든 포메이션은 GK 1 + 필드.
- 목록은 `src/lib/formation.ts` 하나로 합친다. 지금은 `formation.ts`(11인 4종)와 `pitch.ts`(`CURATED` 5·7·11인)에 흩어져 있다.

| 인원 | 포메이션 |
|---|---|
| 5 | 1-2-1 · 2-2 · 3-1 · 1-3 |
| 6 | 2-2-1 · 2-1-2 · 3-1-1 |
| 7 | 2-3-1 · 3-2-1 · 2-2-2 |
| 8 | 3-3-1 · 3-2-2 · 2-3-2 |
| 9 | 3-3-2 · 3-4-1 |
| 10 | 4-3-2 · 3-4-2 |
| 11 | 4-3-3 · 4-4-2 · 4-2-3-1 · 3-5-2 |

- 슬롯 = `{ label, group: GK|DF|MF|FW, x, y }`(0~1 정규 좌표, 세로 피치, 우리 골대가 아래). 줄이 둘이면 DF·FW, 셋이면 DF·MF·FW.
- 경기장: 인원 7 이하면 풋살장(20×40), 8 이상이면 축구장(68×105)이 기본. 토글로 바꿀 수 있다. 슬롯 좌표는 정규 좌표라 경기장이 바뀌어도 그대로다.
- 인원·포메이션을 바꾸면 이미 배치된 선수는 **앞 슬롯부터 순서대로 유지**하고, 넘치는 사람은 벤치로 간다.

### 4.3 배치 규칙

순수 함수로 `src/lib/lineup.ts`에 둔다(단위 테스트 대상).

```
상태 = { count, formation, pitch: 'futsal'|'soccer', slots: (num|null)[], moved: {slot → [x,y]}, drawings: Drawing[], title }
```

| 입력 | 결과 |
|---|---|
| 명단에서 선수 탭(선택된 자리 없음) | 비어 있는 첫 슬롯에 들어간다. 빈 슬롯이 없으면 아무것도 안 하고 토스트 「자리가 다 찼습니다」 |
| 자리 탭 → 선수 탭 | 그 슬롯에 들어간다. 원래 있던 사람은 벤치로 |
| 이미 선발인 선수를 명단에서 탭 | 벤치로 뺀다 |
| 피치 카드를 다른 카드 위로 끌기 | 두 슬롯 교환 |
| 피치 카드를 빈 곳으로 끌기 | 그 슬롯의 위치만 옮긴다(`moved`). 포메이션을 다시 고르면 초기화 |
| 자동 배치 | 슬롯 group이 선수 포지션과 같은 사람 중 OVR 높은 순, 모자라면 남은 사람 중 OVR 순. 지금 `bestEleven`을 인원 일반형으로 바꾼 것 |

모바일에서는 끌기가 불편하므로 **탭 두 번으로 모든 배치가 되게 하고 끌기는 덤**이다. 선택된 자리는 테두리로 표시하고 Esc·바깥 탭으로 푼다.

### 4.4 그리기 방식

캔버스 한 장을 버린다. 크기 계산이 어긋나면 화면 전체가 깨지는 게 지금 문제의 뿌리다.

- 피치 선: SVG(경기장별 viewBox). 지금 스쿼드 피치와 같은 방식.
- 선수 카드: HTML, 슬롯 좌표를 `%`로 절대 배치. 이름 · 포지션 · OVR. D단계에서 사진을 넣을 자리.
- 그림(화살표·펜): 피치 위 SVG 한 겹. 좌표는 정규 좌표로 저장.
- 도구: 이동(기본) · 화살표 · 펜 · 되돌리기 · 지우기. 되돌리기는 그림에만 적용한다.

### 4.5 전술판에서 빠지는 기능

| 빠짐 | 이유 |
|---|---|
| 상대 팀·유니폼 색 | 한 팀 라인업만 |
| 존 도구, 공 | 도구 줄을 모바일 한 줄에 맞추려고. 화살표·펜으로 대신 |
| 줌·핀치, 가로 보기 | 공유 이미지가 세로 한 장 |
| 매치에 저장, 명단 불러오기 | 서버 저장 없음, 명단이 같은 화면에 있음 |

### 4.6 초안

`localStorage` 키 `wfc_squad_draft`에 상태 하나를 저장한다. 바뀔 때마다 쓰고, 들어오면 복원한다. 복원한 선수 번호가 명단에 없으면(탈퇴 등) 그 슬롯은 비운다. 옛 키 `wfc_pitch_draft`는 읽지 않는다.

## 5. 이미지 공유

### 5.1 그림

`src/components/share-image.ts`. 화면 캡처가 아니라 공유용으로 따로 그린다(지금 `recap.ts`의 캔버스 방식).

```
1080 × 1350 (4:5)
┌──────────────────────────┐
│ WEEKLY FC                │
│ 9/20 (토) 라인업   2-2-1  │  ← 제목(수정 가능), 포메이션
│ ┌──────────────────────┐ │
│ │  피치 + 이름·포지션    │ │
│ │  + 화살표·펜 그림      │ │
│ └──────────────────────┘ │
│ 벤치  유성현 · 방오준 · … │
└──────────────────────────┘
```

- 제목 기본값은 오늘 이후 가장 가까운 토요일(`M/D (토) 라인업`). 공유 전에 입력칸에서 고칠 수 있다.
- **OVR은 그리지 않는다.** 단톡방에 능력치 숫자가 도는 것은 민감할 수 있다는 판단(추정). 화면에서는 보인다.
- 색·글꼴은 `tokens.css` 값을 쓴다. 캔버스는 CSS 변수를 못 읽으므로 `getComputedStyle`로 한 번 읽어 넘긴다.

### 5.2 공유 분기

```
[이미지 공유]
 ├─ navigator.canShare({ files: [png] }) 참 → navigator.share (공유 시트 → 카톡)
 └─ 거짓
     ├─ iOS     → 이미지를 크게 띄우고 "길게 눌러 저장" 안내 (src = data URL)
     └─ 그 외   → 같은 미리보기 + [내려받기] (<a download href=data URL>)
```

분기 판단은 순수 함수 `pickShareMethod(env)`로 떼어 테스트한다.

근거: 카카오톡 내부 브라우저는 iOS에서 data URL, Android에서 `<a download>`만 받고 blob URL 다운로드는 둘 다 안 된다([카카오 데브톡 FAQ](https://devtalk.kakao.com/t/topic/146168)). 파일 공유 가능 여부는 `canShare`로 먼저 확인한다([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/canShare)).

## 7. 구현 순서 · 검증 · 배포

```
1. 걷어내기       → 탭 4개, dist 안 죽은 링크 0, 테스트 통과
2. 운영 탭·봉사    → 관리자 모드에서 벌금 추가·납부·당번 수정이 실제 시트에 써짐
3. 포메이션 통합   → 인원별 슬롯 수·group 단위 테스트
4. 스쿼드 한 화면  → lineup.ts 배치 규칙 단위 테스트 + 직접 눌러 배치·교환·벤치
5. 도구           → 화살표·펜·되돌리기·지우기 눌러 확인
6. 이미지 공유     → 뽑힌 PNG를 열어 확인, pickShareMethod 테스트
7. 정리           → 전술판·캔버스 엔진 삭제, 옛 주소 넘김, 상단바 모바일
```

**검증**
- `npm test`(단위 + 빌드 + dist 검사)를 단계마다 통과.
- 데스크톱 1280 · 모바일 390 스크린샷에 더해 배치·교환·그리기·공유를 실제로 눌러 확인한다. 모바일은 바뀐 부분이 뷰포트 안인지까지.
- 1차 검증 항목(가로 넘침 0 · noindex 경계 · 전화 미노출)은 계속 통과.
- `prefers-reduced-motion`에서 새 모션도 꺼진다.

**배포**
- 백엔드 변경 없음 → 프런트만. 브랜치 `squad-ops-restructure`에서 작업하고, push 전에 전/후 화면을 보여주고 승인받는다.
- push는 byjunyoung 계정(`gh auth switch --user byjunyoung`, 끝나면 복귀).

## 8. 범위 밖 · 열린 위험

**범위 밖**: 실사 선수 카드(D단계) · 팀 나누기·상대 팀 · 라인업 서버 저장·링크 공유 · 매치 결과·출석 기록 · 백엔드·시트 변경.

**D단계로 넘기는 충돌**: 2026-09-11 스펙 §4는 "공개 레포에 실명·사진 불가"를 전제로 SVG 아바타를 택했다. 실사 카드는 이 전제를 바꾸는 일이라, 사진을 어디에 둘지(레포 밖 저장소 등)·당사자 동의를 D단계 설계에서 먼저 정한다. 사진 기준은 정해졌다 — **얼굴이 잘 안 보이는 플레이 장면**(뒷모습·옆모습·먼 거리)을 쓴다(사용자 결정 2026-09-13).

**열린 위험**: 카톡 내부 브라우저 공유 동작은 실기기로만 확인된다. 배포 뒤 iOS·Android 폰에서 한 번씩 눌러 본다.
